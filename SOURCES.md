# Data provenance

Following rule 8 of Rule et al. (2019): data are shared with their description, origin and date.
This file is also the model of what students are asked to produce in the format card.

## Current state: synthetic data

Everything in `data/` is generated by `scripts/make_data.py` with a fixed seed (`20260918`). The
structure, encoding and defects reproduce the originals; **the values correspond to no real
measurement and the nine municipalities are invented.**

| File | What it is | Model | Structure | Deliberate defects |
|---|---|---|---|---|
| `aforos_202509.csv` | 21,568 hourly counts from 30 measurement points, September 2025 | Tabular | `DataFrame` | `;` separator, decimal comma, thousands point, `latin-1`, `dd/mm/yyyy` dates, 2,339 `-1` sentinels in speed, 40 duplicated rows, three missing days for detector 1007 |
| `pm_ubicaciones.csv` | Location of the 30 measurement points | Tabular | `DataFrame` | same Spanish conventions; accents in `distrito` |
| `imd_septiembre.xlsx` | Average daily traffic per measurement point | Tabular | `DataFrame` | title and subtitle before the header, merged cells, separate notes sheet |
| `intensidades_2024.xls` | HTML table served with an `.xls` extension, as many public portals do | Tabular | `DataFrame` via `read_html` | **the extension lies**: it is HTML, `read_excel` fails |
| `PZ07_20250915.dat` | TOA5 export of a datalogger, one week hourly | Time series | `DataFrame` | **the extension says nothing**: delimited text with 4 header lines |
| `estructura_rev07.ifc` | Minimal BIM model, three elements, IFC4 | Object with semantics | `ifcopenshell` | STEP text (ISO 10303-21); unknown to students, identifiable from its header |
| `PNOA_2020_0559.las` | 2,000-point LiDAR cloud, LAS 1.2, point format 3 | Point cloud | `laspy` | binary with `LASF` header; only inspected in Exercise 0 |
| `municipios_shp/` | Nine municipalities, EPSG:25830 | Object | `GeoDataFrame` | `superficie_km2` truncated to `superficie` by the 10-character dBase limit |
| `municipios.geojson` | Same municipalities, EPSG:4326 | Object | `GeoDataFrame` | coordinates in degrees, longitude first, as RFC 7946 requires |
| `mdt25_madrid.tif` | Digital terrain model, 25 m, EPSG:25830, 800 × 800 cells | Field | `DataArray` / `rasterio` | no-data value `-32768` in one corner |

Working area: x from 432,000 to 452,000 and y from 4,468,000 to 4,488,000 in ETRS89 / UTM 30N,
which corresponds to the surroundings of Madrid.

## Replacing with real data

Equivalent sources, and what to check in each:

**Traffic counts.** Madrid City Council open-data portal (datos.madrid.es), historical traffic
dataset. One monthly file per measurement point, plus a separate file with detector locations. Cut
to about 20,000 records so it fits comfortably in free Colab memory. Check the reuse licence and
the encoding, which has changed between editions.

**Municipal boundaries.** CNIG download centre (Instituto Geográfico Nacional), municipal boundary
lines. Downloaded as shapefile in the official reference system.

**Digital terrain model.** CNIG download centre, MDT25 or MDT05 depending on the resolution wanted.
One tile is enough. MDT05 is heavier and must be clipped.

**Average daily traffic.** Ministry of Transport traffic map, or the Madrid portal itself, for the
spreadsheet with multiple header rows.

When replacing:

1. Record here the exact URL, download date and licence of each file.
2. Re-run `python scripts/make_data.py --comprobar` or compute the expected values by hand, and
   update the asserts in the notebooks and the reference table in the README.
3. Regenerate the figures with `python scripts/make_figures.py`.
4. Run both solution versions end to end.
5. Freeze a copy in the course repository, so that the class does not depend on the portal being
   up on Friday morning.

## Warning about download paths

Portals reorganise their catalogues frequently and paths expire. The descriptions above are of
products, not URLs. Check the portal before downloading.
